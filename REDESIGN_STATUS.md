## Ordering rules

1. **The branch is pushed only after the preview database slice is committed.** Every pushed branch gets a Cloudflare Pages preview. Before `[env.preview]` existed in `wrangler.toml`, that preview was bound to the production database `lca-db`, so anyone clicking around it would have written real registrations and accounts. `redesign/ws01-design-system` stays local until the commit that adds the preview database. Before that first push, K also checks the Preview environment's secrets in the Pages dashboard and removes any live Stripe or Resend key: previews existed before this slice and may already hold the live ones.
2. **K migrates the preview database from the branch before reviewing each checkpoint's preview.** He runs `npm run db:migrate:preview` from the branch, with his own Cloudflare credentials, before he looks at the preview, not after the merge. Merging to `main` migrates production only (`.github/workflows/migrate-db.yml`); nothing migrates `lca-db-preview` automatically. Once the branch adds tables the code reads (the sections and schedules tables), a preview bound to an unmigrated database shows errors.

### Step 3: shared `domain/` folder and formats

- New folder `domain/` at the repo root for pure code that the site, the server functions and the workers all use: no database access, no DOM, no Workers types and no React. This step creates `domain/format` only; the other areas (events, registration, households, membership, clubs, live, contracts) are created by the steps that fill them.
- `domain/format` holds `formatScore` (3.5 is "3½", 0.5 is "½", 0 is "0", 10 is "10"), `formatDate` ("Sat, Oct 24", or "Sat, Oct 24, 2026" with the year option), `formatTime` ("7:00 PM", with "12:00 PM" at noon and "12:00 AM" at midnight) and `formatTimeControl` ("G/90+30" becomes "G/90+30 · 90 min each + 30 sec per move"; "G/30;d5" adds "30 min each + 5 sec delay"; "G/60" adds "60 min each"; text it does not recognise comes back unchanged). `describeTimeControl` gives the plain words on their own.
- How values are read: a bare stored date or datetime-local value ("2026-10-24", "2026-10-24T19:00") is Louisiana wall-clock time and is shown as written; a Date, epoch milliseconds or an ISO string with a zone is an instant and is shown in Central time. Columns filled by SQLite's `datetime('now')` (`created_at`, `updated_at`, `sent_at`, `recorded_at` and the like) look like wall-clock text ("2026-10-24 02:30:00") but hold UTC, as the admin audit log, board seats and board inbox already assume by appending `Z`; `formatDate` and `formatTime` read them as UTC when passed `{ stored: 'utc' }` (that example is "Fri, Oct 23" at "9:30 PM"), and the `date.ts` header says those columns must be passed that way. The default stays wall-clock because announcement start and end times are stored as Louisiana time in the same text form. Weekday and month names, and the "7:00 PM" text, are built from fixed tables rather than by `Intl`, so the text is identical in browsers, Node and Workers (newer locale data puts a narrow no-break space before "PM"). A string a helper cannot read is returned as given, so a bad value shows up rather than vanishing.
- `src/lib/format.ts` is one line, `export * from '@domain/format'`, so the brief's path works. Nothing in the site uses the helpers yet, so nothing visible changes and no switch is needed; pages adopt them behind `newLook` in later steps.

It exports `EventPhase` and `EVENT_PHASES` (the nine phases the brief names: `week`, `dayBefore`, `checkin`, `eventDay`, `roundPosted`, `roundInProgress`, `between`, `final`, `after`), `eventPhase(input, now)`, `phaseKey(eventId, phase, round)`, and three helpers for the WS02 endpoint and the client's window gate: `eventEndMs`, `eventModeWindow` and `firstRoundTimesFromSchedule`.
- The input is a plain object, `{ date, endDate, status, firstRoundTimes, lastRoundResultsComplete }`. `firstRoundTimes` is keyed by the event day ("YYYY-MM-DD") with that day's first `round_schedule` time ("HH:MM") or null. A null, blank or unreadable value means the day has a round whose time is not set yet. A day with no key has no round (an off day), provided at least one day of the event has a key; with no key inside the event at all, every day counts as not set. `firstRoundTimesFromSchedule(round_schedule, date, end_date)` builds it from the stored schedule (earliest time per day; a day with no round has no key only when every round is dated inside the event, otherwise each such day is null).
- Every boundary is a Louisiana wall-clock time turned into an instant with `lcaTimeToMs` (`domain/format/centralTime.ts`); the Central calendar day of `now` comes from `zonedParts` (`domain/format/date.ts`). Calendar days are counted with `Date.UTC`, so no local-time method is used. `eventEnd` is 11:59 PM on `end_date ?? date`, and the 48 hours of `after` are real elapsed time: across the November change the window closes at 10:59 PM, and across the March change at 12:59 AM.
- `phaseKey` is `${eventId}:${phase}:${round ?? 0}`, the brief's `key`. `week` and `dayBefore` come back on off days between playing days, and `checkin` and `eventDay` on each playing day, so the caller passes a round for them: the first round of the next playing day for `week` and `dayBefore` (1 before day 1), the first round of that day for `checkin` and `eventDay`. Without it, a strip hidden on the day before day 1 would stay hidden on the day before round 2. The doc comment says so and a test shows the two keys differ.
- `roundPosted`, `roundInProgress` and `between` are in the type but never returned; the doc comment says they wait for WS07's round publications and live state, when `checkin` will end at the round 1 publication and `eventDay` will stop being produced.
- Where the brief leaves a moment without a phase, the rule is under Decisions ("Event-mode phase gaps"). Where the module goes against the brief's text (`eventDay` past 11:59 PM, and `after` from 6:00 AM for an event that is not final), the rule is under Deviations ("Event-mode phase times"). The module's doc comment lists both as going beyond the brief.

  - `week` changes to `dayBefore` at midnight starting the day before, as the brief says. `dayBefore` then runs on through the night until 6:00 AM on day 1, the gap the brief leaves between "the calendar day before" and check-in at 6:00 AM.
  - A day whose round has no time set (a null, blank or unreadable value) stays in `checkin` all day (the strip's "time to be announced" line, and the TD's "Round times missing" fix-it). A first round time before 6:00 AM makes the day `eventDay` from 6:00 AM.
  - A day between `date` and `end_date` with no round in the schedule (no key in `firstRoundTimes`, while other days of the event have one) is not a playing day, so it is never `checkin`. From 6:00 AM it is `dayBefore` when the next round day is the next calendar day, `week` when the next round day is further off (a one-round-a-week event), and `eventDay` when no round day is left before `end_date`. So a Fri to Sun event with no Saturday round is `dayBefore` all Saturday, polls at the slow rate and raises no fix-it. When no key falls inside the event at all, the schedule is not written yet and every day is "time to be announced".
  - A day counts as having no round only when the whole schedule is dated inside the event. `firstRoundTimesFromSchedule(schedule, date, endDate)` takes the event's days for this: when any round has a blank or unreadable date, or a date outside the event (a typo, or a schedule left on the old dates after the event moved), every event day with no round of its own gets null, so it stays `checkin` with "time to be announced" and the TD's "Round times missing" fix-it still appears. Rounds dated outside the event are left out. So a Fri to Sun event with only round 1 dated is `checkin` all Saturday and Sunday, not `eventDay`.
  - `final` (status `completed`, or results in for every section's last round) wins over the calendar phases inside the window and lasts until 11:59 PM on the last day; from then until 48 hours later it is `after`. Outside the window the result is null even for a completed event.
  - An `end_date` that is missing, unreadable or before `date` means a one-day event. A `date` that is not a calendar day gives null.
