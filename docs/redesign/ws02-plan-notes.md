## Why this order

- **The record first.** Step 1 maps every criterion and decision to its step before anything is built, so each step fills in a line that already exists and the close-out only checks that none is left planned. It also fixes the stale "merge pending" wording while the facts are fresh, and makes PR 106's test changes if they did not land.
- **The model and the harness before any chrome.** Every bar, menu and list reads `nav.ts`, and every signed-in criterion (the Join and Renew slot, the My LCA menu, the strip) needs a signed-in visitor in the browser tests, which the test servers cannot give today: their sign-in service is a closed local port, and WS01 left signed-in pages untested for that reason. The chrome's one condition is set here too, so no later step has to decide what its part draws without `newLook`.
- **The frame before the header.** The skip link, the loading line, theme-color and the rings are shared by every chrome piece; building them once means the header, the sheet, the dock and the footer only apply them. It is also WS02's first change to `src/index.css`, where the brief puts the `@source not` lines.
- **The specs' reads before the header.** The a11y-on build has `newNav` on from step 2, so every spec that reads today's header or footer there changes as the new chrome is drawn. Measured in planning, 56 lines of code read the header and 75 the footer, in 11 specs (about 200 lines in 15 with their comments). Step 4 moves those reads into one helper with nothing drawn differently, so the header's step adds a header without also reworking a dozen specs, and each later chrome step changes the helper's answer rather than every spec.
- **The sheet before the tab bar.** The Menu tab opens the sheet, and AC3 is about focus returning to the tab; building the sheet first (opened from the tablet's and the app bar's Menu buttons) leaves no step with a button that opens nothing.
- **The footer last of the static chrome.** AC8, AC11, AC13 and AC18 hold only when the header, the sheet, the tabs and the footer all exist, so they are proved in the footer's step.
- **The endpoint before the panel; the words before the endpoint.** The search panel is built against real answers. The event-mode endpoint writes the "Players see" echo, so the copy builder comes first, in `domain/`, where the endpoint and the site both read it.
- **Search and the strip in two steps each.** The combobox, the panel and the trigger come first and `/search`, the Popular list and Your tools after; the hook and the strip come first and the Live tag, its 204 endpoint and the support form after. Each first half is the larger, and each is proved before the next builds on it.
- **The My LCA menu last among the parts.** It gathers the to-dos (from `/api/me`'s new fields, step 13), the event line (from the strip, step 14) and the rows `nav.ts` gives.
- **The matrix after everything.** AC1 (the whole bar with Search, Renew and the Live tag), AC14 (axe with the strip and the tab bar drawn) and AC19 (the rings on every surface) can only be measured with every part in place, as WS01's AC1 waited for step 32. `/contact` and `/support` join it then, after the steps that change them.

## Risks

- **WS01's tests are brittle.** The record tests read the whole status file and the spec's WS01 line, and `test/unit/test-setup.test.ts` reads the spec's switch table, so a WS02 table, a heading that starts "### Step", or brief 1.4's restructured bullet and new switch rows can fail them. PR 106 and step 1 handle the brief's part; each step maps the readers it meets and writes around them; no pin is deleted, and every pin that moves keeps its meaning.
- **Today's chrome under `newLook` loses its browser build.** Once the new chrome draws at every width on a11y-on (step 6), no browser build draws today's header and footer under `newLook`, the state K turns on first. Step 4 keeps a jsdom form of each WS01 check of them that can have one, and lists the rest, which only a browser reads, for K's preview of `newLook`.
- **The signed-in harness leans on how the installed sign-in library keeps a session.** Its own spec fails loudly if a version change breaks it, and it never touches a real sign-in service.
- **The widest desktop row may not fit.** The phase 0 replan's width budget for 1024 pixels was about 985 pixels for 976 before the squeeze. If Renew with the Live tag does not fit after both squeeze steps, the figures go to K; no section or utility leaves the bar on the plan's own authority.
- **Phone heuristics.** Telling an open keyboard from a short screen, and high zoom from a small phone, differs by browser; each rule chosen is recorded and tested with a narrowed viewport, and K looks on a real phone.
- **New endpoints go live before their switches.** Search answers only listed, public rows, cached at the edge for 60 seconds, with no rate limit until WS07's helper; event-mode answers only a person's own events; live-now answers 204. Each checkpoint's section says so.
- **Polling cost.** The strip polls every 20 seconds through an event day for each involved person with the page open; the window, the ETag and the hidden-tab rule bound it, and step 13 records what a poll costs.
- **Words the table does not hold.** Event mode's lines for later playing days, earlier check-ins and off days are written in the phase 0 table's patterns, not by K; the record lists each for K to read on the preview.
- **The five early switches.** Turning one on before its workstream re-points rows at pages that do not exist, and `myLcaRail` takes the role rows out of the menu with no rail behind them; a unit test fails any pull request that does either (for `myLcaRail`, while `/workspace/lookup` is not a route), but a throwaway preview branch runs no tests, so each comment says to leave it off.
- **PR 106 and the stylesheet.** Until step 3's `@source not` lines land, the docs branch's boards add class rules to the site's stylesheet when PR 106 merges; bytes only, measured on that PR.
